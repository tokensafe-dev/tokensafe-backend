# OUMV measured agent matrix

> Generated by `tokensafe bench-oumv`. Every token and cost number below comes from the
> provider's `usage` payload and a real 12-assertion oracle; no trace replay, no estimation.

## Correction (post-run diagnosis, 2026-11-26)

The `tokensafe` row below ran an **incomplete and mis-prompted** version of the product's
toolkit, so it overstates the cost of using TokenSafe. Diagnosed from the recorded traces:

- The arm exposed only the read half of the toolkit (`smart_read_file`, `scoped_search`,
  `repo_map`) and no `apply_edits`, so every edit was a blind `write_file` + `go test`
  retry loop. The product ships `apply_edits` with inline `verify`.
- Its system prompt was a tool menu — *"use them before reading whole files"* — with no
  procedure and no stopping rule, while the `oumv` arm got a numbered four-step loop.
  Mean steps: 10.7 (tokensafe) vs 4.4 (baseline) vs 4.0 (oumv).
- `smart_read_file` returned a folded whole-file skeleton **with a header claiming
  "Full body"** whenever the requested symbol was not a declaration in that file — the
  normal case for a Go route handler (an anonymous closure inside `NewVanillaApp`). The
  agent paid for the call, got nothing actionable and re-read the file: `read_file`
  chars/run were 12,635 for this arm vs 13,102 for baseline, i.e. **no read saving at
  all**, plus ~5 KB/run of the arm's own output.
- Two of nine runs died at `max_steps` repeating an identical build error.

Fixed since this run: `smart_read_file` resolves the symbol against the file's
declarations first and returns the enclosing handler (±window with line numbers) or an
honest miss; it accepts endpoint targets (`POST /api/orders`); `scoped_search` groups hits
per file and caps a hot file's share of the budget; the arm now runs the product's real
loop (`scoped_search` → `smart_read_file` → `apply_edits` + inline `verify`). The
`baseline` and `oumv` rows are unaffected. **The `tokensafe` row is superseded and must not
be quoted until it is re-measured.**

## Method

| | |
| :--- | :--- |
| Model | `deepseek-chat` (temperature 0) |
| Price snapshot | 2026-11-26: input $0.27 / Mtok (cache miss), $0.07 (cache hit), output $1.1 |
| Runs | 3 per task per arm |
| Budget cap | $5.0 per target (hard stop) |
| Harness revision | cc92633f91be1d898ca5c762ebac18a98114a6f0 |

All three arms get the same file/search/command tools and the same bug report, including
a repro. `oumv` adds observe/getSource/applyEdit/verify/understand from the shipped
adapter; `tokensafe` adds the product's own smart_read_file/scoped_search/repo_map over
the real MCP server. Each session starts from a throwaway copy of the sandbox with one
deliberate regression, and the oracle is re-run after every step.

## Limits

- One model (`deepseek-chat`, temperature 0), one vendor; three tasks per target.
- The sandbox is small (a 155-line Go app): discovery cost is lower than in a large repo, so
  these numbers are a floor for the discovery saving, not a ceiling.
- The `tokensafe` arm ran the real MCP server, but an incomplete slice of it (no
  `apply_edits`) with a procedure-free prompt, and `smart_read_file` returned an
  unusable skeleton for closure handlers. See the correction above; the row is superseded.
- `oumv/verify` starts a fresh app per call by design, so stateful failures are confirmed
  with the test oracle in both arms. Multi-step verify is a spec-backlog item.
- `verify.steps` and `applyEdit mode=symbol` ship in v1.1 but these tasks are one-line
  status changes; the agents used whole-file edits, so edit-side savings are not measured
  by this matrix.
